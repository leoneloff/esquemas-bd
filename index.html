1. Introducción: de los datos al modelo

Una base de datos es un conjunto organizado de datos relacionados que permite almacenar, consultar, actualizar y administrar información. No se trata solo de “hacer tablas”: hay que analizar necesidades, definir datos, establecer relaciones, controlar seguridad y dejar espacio para que el sistema evolucione.

🎯
Objetivo de un buen diseño:

Representar fielmente la realidad, mantener integridad, ofrecer buen rendimiento y permitir cambios futuros. La base de datos es un sistema vivo, no un archivo estático.

Base de datos

Almacena información estructurada. En una escuela: alumnos, profesores, materias, grupos, inscripciones y calificaciones, recuperables con consistencia.

SGBD / DBMS

Software que crea estructuras, ejecuta SQL, aplica integridad, controla usuarios, administra transacciones, respalda y recupera. Ejemplos: PostgreSQL, MySQL, Oracle, SQL Server, MongoDB, Redis, Neo4j.

Modelo de datos

Forma de representar cómo se organizan los datos y sus relaciones: relacional, jerárquico, red, documental, clave-valor, grafos, dimensional, etc.

Entidad, atributo, relación y cardinalidad

El modelo Entidad-Relación (ER) es la herramienta del diseño conceptual. Una entidad es un objeto identificable (Cliente, Producto). Un atributo lo describe (nombre, correo). Una relación conecta entidades. La cardinalidad indica cuántas veces participa cada una: 1:1, 1:N o N:M.

Una relación N:M casi siempre se convierte en una entidad intermedia. Alumno y Materia se unen con Inscripción (id_alumno, id_materia, fecha, calificación).

🏛️ Ejemplo de requisitos: biblioteca (no basta con “registrar libros”)

Antes de crear tablas hay que aclarar reglas del negocio:

  • ¿Un libro puede tener varios ejemplares?
  • ¿Un autor puede escribir varios libros?
  • ¿Cuántos días dura un préstamo y qué pasa si se entrega tarde?
  • ¿Se conservan préstamos históricos?

Sin esas respuestas, el esquema queda incompleto aunque “compile” el SQL.

2. Arquitectura ANSI-SPARC de 3 niveles

La arquitectura de tres niveles separa lo que ve cada usuario, la estructura lógica global y el almacenamiento físico. El objetivo principal es la independencia de datos: cambiar un nivel sin reescribir el superior. Los mapeos traducen peticiones entre capas.

🔍 Diagrama completo: de la pantalla al disco

Nivel externo Vistas por usuario o aplicación: portal del alumno, pantalla del cajero, reporte de gerencia. No ve toda la base.
↕ Mapeo externo / conceptual
Nivel conceptual Esquema lógico global: entidades, relaciones, CHECK, UNIQUE, PRIMARY KEY. Independiente del disco. Lo define el DBA.
↕ Mapeo conceptual / físico
Nivel interno (físico) Archivos, índices B-Tree, particiones, compresión, páginas de disco, réplicas. Cómo se guarda realmente.
Vista alumno

Solo ve sus materias y calificaciones. No ve sueldos ni índices.

Vista cajero

Ve productos, precios y existencias. No ve el historial médico ni el plan de ejecución SQL.

Vista DBA

Administra el esquema conceptual y decide índices, respaldos y permisos en el nivel interno.

Nivel externo

El más cercano al usuario. Pantallas, reportes y APIs. Varios esquemas externos pueden coexistir sobre el mismo esquema conceptual.

Nivel interno

El más bajo. Define almacenamiento, direccionamiento, índices y particiones. Un cambio de HDD a SSD ocurre aquí, no en la interfaz.

El DBA comprime la tabla de historial para ahorrar disco.

3. Nivel conceptual e independencia de datos

El nivel conceptual es la representación abstracta e integral de toda la base: qué datos se almacenan y cómo se relacionan, sin decir cómo se guardan en disco. Es independiente de hardware y software. Solo el DBA define este nivel; describe la estructura para todos los usuarios.

Dos fases de modelado en el nivel conceptual

1. MER / DER

Rectángulos (entidades), rombos (relaciones) y elipses (atributos). Describe el negocio sin escribir SQL.

2. Esquema conceptual (DDL)

Se materializa con CREATE TABLE, PRIMARY KEY, FOREIGN KEY, UNIQUE y CHECK. Sigue siendo lógico, no físico.

🛡️ Independencia: el mapeo absorbe el cambio

En archivos tradicionales, cambiar el formato en disco obligaba a reescribir las aplicaciones. Aquí el SGBD actualiza solo el mapeo.

Independencia lógica

Cambiar el esquema conceptual (agregar tabla o columna, dividir una entidad) sin modificar vistas externas ni aplicaciones. El mapeo externo/conceptual se actualiza.

Independencia física

Cambiar el nivel interno (HDD→SSD, índices, particiones) sin tocar el esquema conceptual ni las pantallas. El mapeo conceptual/físico se actualiza.

🧩
No confundir con diseño conceptual / lógico / físico del ciclo de vida.

ANSI-SPARC habla de capas en tiempo de ejecución. El ciclo de vida habla de etapas de proyecto: primero se modela el negocio, luego tablas, luego índices. Se parecen, pero no son lo mismo.

✍️ Problema 3: ¿lógica o física?

Para cada caso, decide el tipo de independencia. Piensa qué mapeo se actualiza.

  1. La empresa cambia HDD por SSD y el formato de archivos. El software de ventas no se toca.
  2. Se agrega la columna edad a Cliente. El kiosco de autoservicio sigue mostrando solo nombre y precio.
  3. Se crea un índice sobre VENTA.fecha para acelerar reportes mensuales.
  4. La tabla Empleado se parte en Empleado y Departamento (3FN). Las vistas de RH se redefinen en el mapeo, no en cada pantalla.
Ver respuestas
1. Física (hardware y archivos).
2. Lógica (cambia el esquema conceptual; la vista externa no).
3. Física (índice = estructura interna).
4. Lógica (reestructura de tablas; las apps siguen pidiendo los mismos datos lógicos vía vistas).

4. Tipos de esquemas según el modelo de datos

El esquema es la descripción de la estructura. Distintos modelos sirven a distintos problemas: consistencia bancaria, documentos web, amigos-de-amigos o analítica de un almacén de datos.

Modelos clásicos

Clásico

Relacional

Tablas 2D, filas y columnas. PK, FK y normalización. Estándar en MySQL, PostgreSQL y SQL Server. Ideal cuando la consistencia es crítica (banco, nómina, escuela).

Clásico

Jerárquico

Árbol padre-hijo 1:N. Cada hijo tiene un solo padre. Rígido para relaciones complejas. Aparece en sistemas antiguos.

Clásico

En red

Grafo: un hijo puede tener varios padres (N:M). Extiende al jerárquico para interconexiones complejas. Típico en sistemas heredados.

Objetos, NoSQL y dimensionales

OO / híbrido

Orientado a objetos

Clases, atributos, métodos, herencia y encapsulamiento. El objeto-relacional mezcla tablas con tipos definidos por el usuario.

NoSQL

Documentos

Colecciones JSON/BSON (MongoDB). Flexible cuando el documento no cabe en filas rígidas.

NoSQL

Clave-valor

Pareja clave → valor. Muy rápido para caché y sesiones (Redis).

NoSQL

Grafos

Nodos y aristas. Redes sociales, rutas, “amigos de amigos” (Neo4j).

NoSQL

Columnar

Datos por columna, no por fila. Analítica masiva (Cassandra, almacenes columnares).

DW

Estrella y copo de nieve

Estrella: hechos al centro y dimensiones alrededor. Copo: las dimensiones se normalizan en subtablas. Pensados para Business Intelligence.

Relaciona necesidad y modelo. Hay más de una trampa deliberada.

  2. Banco: consistencia absoluta, filas, columnas y reglas estrictas.
  3. Tienda: analítica histórica de ventas con tiempo, cliente y producto (BI).
  4. Sitio web: perfiles de usuario con campos que cambian cada mes, guardados como JSON.
  5. Caché de sesiones de login que debe responder en microsegundos.
  6. IMS antiguo de un mainframe con departamentos y un solo jefe por empleado.

5. Herramientas, normalización y ciclo de vida

El diseño convierte una necesidad de información en una estructura eficiente. Se recorre en tres niveles de proyecto: conceptual (independiente del SGBD), lógico (tablas y claves) y físico (índices, particiones, memoria, respaldos).

Herramientas

  • Requisitos: entrevistas, casos de uso, prototipos, observación de procesos.
  • Diccionario de datos: nombre, tipo, longitud, obligatoriedad y restricciones de cada campo.
  • ER y UML: comunicación con usuarios y con programadores.
  • CASE: MySQL Workbench, pgModeler, DBeaver, ERwin, Draw.io… generan diagramas y a veces SQL.
  • SQL y migraciones: V1__crear_clientes.sql, Flyway o Liquibase para no cambiar producción a mano.

⚙️ Diccionario + SQL mínimo

CampoTipoLongitudRestricciones
id_alumnoEntero—Obligatorio, PK
nombreTexto80No vacío
correoTexto120Formato válido, UNIQUE
CREATE TABLE Cliente (
  id_cliente INTEGER PRIMARY KEY,
  nombre VARCHAR(100) NOT NULL,
  correo VARCHAR(150) UNIQUE
);

CREATE INDEX idx_cliente_correo ON Cliente(correo);

El índice acelera búsquedas, pero ocupa espacio y puede ralentizar INSERT/UPDATE. No se crean “por si acaso”.

Normalización (calidad del diseño)

1FN

Valores atómicos, sin listas en una celda. Incorrecto: materias = "Mate, Física". Correcto: una fila por materia.

2FN

Todo atributo depende de toda la clave primaria (clave compuesta).

3FN

Nada depende de un no-clave. El nombre del departamento no se copia en cada empleado: va en tabla Departamento.

Normalizar reduce anomalías de inserción, actualización y borrado. Desnormalizar solo con justificación (rendimiento analítico) y controles.

Ciclo de vida

1

Planificación y alcance. Objetivo, presupuesto, riesgos. ¿Base nueva o producto comercial?

2

Análisis de requisitos. Datos, usuarios, reportes, confidencialidad, volumen de transacciones.

3

Diseño C-L-F y elección del SGBD. Modelo ER → tablas → índices. Licencia, seguridad, escalabilidad.

4

Implementación y carga. Tablas, permisos, procedimientos, migración validada.

5

Pruebas. Unitarias, integración, rendimiento y seguridad. Probar también la restauración de respaldos.

6

Operación, mantenimiento y retiro. Monitoreo, mínimo privilegio, versionado. Al final, archivo y apagado controlado.

🛒 Caso: sistema de ventas

Lógico: CLIENTE, VENTA, PRODUCTO, DETALLE_VENTA (cantidad, precio_unitario). Un cliente muchas ventas; una venta muchos renglones; un producto en muchos detalles.

Físico: índices en fecha y id_cliente; no permitir existencias negativas; respaldo diario; roles distintos para vendedor y admin.

 WHERE id_producto = 25 AND existencia >= 2;

⚠️ Problemas frecuentes vs buenas prácticas

Evitar

  • Crear tablas sin requisitos
  • Sin PK, nulos sin control, varios valores en una columna
  • Permisos excesivos y cambios directos en producción
  • Nunca probar restaurar un backup

Practicar

  • Involucrar usuarios y documentar reglas
  • Separar conceptual, lógico y físico
  • Restricciones en la base, no solo en la app
  • Versionar, mínimo privilegio, medir rendimiento
